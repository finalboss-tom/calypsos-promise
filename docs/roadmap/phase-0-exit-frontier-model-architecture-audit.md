# Phase 0 Exit — Frontier-Model-First Architecture Audit and Build Authorization

**Status:** BASELINE transition gate; execution remains deferred until the other Phase 0 closure work is ready for integrated review.

**Authority:** This audit implements the Phase 0 exit gate in the [Public Institutional Roadmap](../../ROADMAP.md). It does not replace the Product Constitution, frozen Architecture Foundation, accepted decisions, security holdpoints, specialist review, or ordinary pull-request acceptance.

## Purpose

Calypso’s Promise is beginning at a point when frontier models can hold and reason across a substantial representation of the project’s mission, governance, architecture, schemas, incentives, lore, roadmap, and implementation state. The project intends to use that capability as a primary cognitive development layer while expecting context capacity, price-performance, tool use, and model capability to improve over time.

That opportunity is valuable only if the architecture preserves durable authority outside any model, remains useful when effective context is smaller than an advertised limit, and can adopt better models without redesigning the product around one provider or one generation of inference.

This audit is therefore a mandatory Phase 0 closure activity and the final architecture gate before Phase 1 private-product implementation begins.

## Binding transition rule

> Frontier models may be the project’s primary cognitive development layer. The repository, deterministic domain services, reviewed records, tests, provenance, and accepted governance artifacts remain the project’s durable memory and authority.

No Phase 1 private-product implementation may begin until the audit produces an explicit build-authorization record that is accepted and merged.

Public, synthetic, documentation, contract, validation, and repository-tooling work may continue during Phase 0 when it remains within its accepted scope. This gate blocks premature private-product and production architecture, not the safe completion of Phase 0 evidence.

## Architectural thesis to test

The audit must test rather than merely restate the following thesis:

1. the current repository is sufficiently structured for a frontier model to reconstruct the project’s purpose and relevant implementation context;
2. ordinary development can operate from bounded, task-specific context packages rather than requiring a full-repository prompt for every change;
3. whole-repository frontier-model passes can provide valuable reconciliation, contradiction detection, dependency review, and long-horizon reasoning;
4. context-window growth, lower inference prices, better caching, retrieval, memory, tools, and agent coordination can improve efficiency without becoming correctness prerequisites;
5. model and provider substitution can occur without changing Chronicle truth, House of Keys authority, gameplay truth, security policy, governance authority, or the player promise; and
6. model output remains a proposal until accepted through the project’s deterministic, evidentiary, and human-accountable controls.

A coherent architecture is not evidence that this thesis is true. The audit must record what is demonstrated, what remains a working hypothesis, and what would invalidate or narrow the approach.

## Required audit scope

### 1. Constitutional and authority integrity

Review the complete repository against the Product Constitution, Vision, frozen Architecture Foundation, Gameplay Foundation, accepted decisions, institutional roadmap, status vocabulary, and current implementation.

The audit must identify:

- contradictions, duplicate authority, stale claims, hidden decisions, and unresolved terminology;
- any path where model, retrieval, memory, tool, provider, workflow, or generated content can acquire authority by convenience;
- any path where source truth, Chronicle truth, permission truth, execution truth, receipt truth, gameplay truth, funding truth, governance truth, and model proposals are blurred; and
- any requirement that exists only in chat, private notes, model memory, or an unreviewed generated summary.

### 2. Repository context architecture

Define how a model receives the right project context for a task.

The design must include:

- a compact constitutional kernel that remains available for material work;
- a machine-readable authority and status map;
- task-specific context manifests;
- dependency, ownership, and affected-surface discovery;
- source revision, path, authority class, and evidence-level provenance;
- explicit prohibited and protected sources;
- context budgeting that reserves room for reasoning, tools, and structured output;
- retrieval, compaction, caching, and refresh behavior;
- stale-context detection and reconciliation;
- conflict handling when sources disagree; and
- a full-repository audit path distinct from ordinary task execution.

The repository must not be treated as one undifferentiated prompt. The audit must define a context compiler or equivalent process that assembles deliberate, inspectable working sets.

### 3. Effective-context evaluation

Advertised context capacity must not be treated as proof that all included information was understood or applied.

The audit must evaluate:

- evidence located near the beginning, middle, and end of large contexts;
- competing, duplicated, stale, superseded, proposed, historical, and adversarial records;
- multi-hop reasoning across architecture, governance, schemas, tests, and roadmap documents;
- selective attention under irrelevant volume;
- retrieval omissions and incorrect retrieval ranking;
- context compaction loss;
- contradictory source precedence;
- tool-result contamination and prompt injection; and
- output quality as context volume and task complexity increase.

The result must define a measured operating profile for ordinary tasks and a separate measured profile for whole-repository review. Nominal model limits alone do not satisfy this gate.

### 4. Model and provider architecture

Define a provider-independent model boundary covering:

- capability and risk classes;
- model selection and fallback;
- context, output, latency, reasoning, and cost budgets;
- prompt and prefix caching where supported;
- structured input and output contracts;
- timeout, cancellation, retry, duplicate, stale-result, and provider-unavailable behavior;
- model and provider version recording;
- evaluation and migration requirements;
- concentration, credits, sponsorship, affiliate, and related-party conflicts;
- replacement and teardown; and
- complete non-AI paths for constitutional personal-core behavior.

No provider, model, context window, benchmark, service credit, or sponsored evaluation may become domain authority or an irreversible architecture dependency.

### 5. Agent and tool authority

Review every current and planned agent, MCP, workflow, retrieval, memory, and tool surface.

The architecture must preserve:

- server-owned tool identity, schemas, risk classes, scopes, and limits;
- least authority and explicit user or steward confirmation where consequence warrants it;
- separation between planning, drafting, validation, execution, and acceptance;
- source-linked inputs and public-safe receipts;
- no arbitrary shell, filesystem, network, database, provider, repository, or governance authority by default;
- untrusted retrieved and generated content remaining data rather than instructions;
- deterministic validation before canonical effects;
- cancellation, containment, rollback, correction, and supersession; and
- attributable human or institutional authority for consequential release and governance decisions.

### 6. Durable memory, provenance, and state

Define what must persist outside model context and where it belongs.

The audit must distinguish:

- repository and decision history;
- authoritative domain state;
- source artifacts and provenance;
- player-visible Aster memory;
- retrieval indexes and rebuildable projections;
- task-local working memory;
- operational state and delayed work;
- protected audit and public receipts;
- model and tool traces; and
- ephemeral caches.

No material project decision, personal right, canonical record, permission, release fact, or governance state may depend on an opaque conversation history or provider-retained memory.

### 7. Private-data and security boundary

The audit must prove that public or contributor model use remains compatible with the permanent rule:

> The software is open. The person’s health data is private.

It must define separate gates for any future protected-data model use, including purpose, minimum necessary disclosure, provider and subprocessor review, retention, training use, region, access, encryption, logging, deletion uncertainty, incident handling, user control, non-AI fallback, and provider exit.

A model’s context capacity does not authorize broader collection, retention, aggregation, or disclosure.

### 8. Runtime and module architecture

Reconcile the planned product against the modular-monolith default and accepted domain boundaries.

The audit must produce or confirm:

- bounded application and package responsibilities;
- dependency direction;
- authoritative write ownership;
- responsive and deferred paths;
- commands, events, jobs, projections, schedules, receipts, and audit boundaries;
- provider and infrastructure adapters;
- local and synthetic substitutes;
- module-creation and service-extraction gates;
- failure, recovery, replay, correction, migration, and teardown behavior; and
- the smallest Phase 1 implementation slice that proves personal value without prematurely selecting the final production topology.

Larger model context must not become an excuse for a poorly decomposed codebase or hidden cross-domain coupling.

### 9. Developer experience and continuous development

Define how frontier models participate in ongoing development without replacing reviewable engineering discipline.

The design must cover:

- repository orientation for humans and models;
- issue-to-context-to-change traceability;
- task contracts and acceptance criteria;
- patch-sized output rather than unnecessary repository rewrites;
- tests, static checks, architecture checks, and evaluation gates;
- model-assisted review separated from independent review where independence matters;
- generated-code provenance and attribution;
- clean-machine and second-operator workflows;
- cost, latency, failure, and context-consumption observability; and
- maintenance when the preferred model or provider is unavailable.

### 10. Future leverage and migration

The architecture must explain how future improvements can be adopted safely:

- larger effective context;
- lower input and output prices;
- better caching and retrieval;
- stronger multimodal understanding;
- longer structured output;
- more reliable tool use;
- persistent memory;
- parallel and specialized agents; and
- local or open-weight alternatives.

Each improvement should reduce orchestration cost, increase review coverage, or improve fidelity. It must not silently expand authority, private-data exposure, retention, vendor lock-in, or unsupported product claims.

## Required deliverables

The Phase 0 exit audit must produce, at minimum:

1. **Whole-repository consistency audit** — findings, contradictions, stale records, duplicate authority, unresolved decisions, and remediation status.
2. **Architecture build map** — applications, packages, domains, authority owners, dependency directions, trust boundaries, adapters, data flows, and planned Phase 1 slice.
3. **Canonical context map** — constitutional kernel, authority hierarchy, status sources, machine-readable manifests, protected paths, and refresh rules.
4. **Context compiler design** — task intake, affected-surface discovery, retrieval, budgeting, compaction, caching, source precedence, provenance, and output contract.
5. **Model and provider gateway contract** — capability classes, routing, budgets, provider neutrality, fallbacks, versioning, evaluation, migration, and teardown.
6. **Agent and tool authority matrix** — permitted actions, confirmation requirements, prohibited authority, receipts, containment, and rollback.
7. **Durable memory and state map** — authoritative state, source artifacts, model-visible memory, indexes, operational state, traces, caches, retention, export, and deletion.
8. **Long-context and context-engineering evaluation suite** — representative tasks, adversarial cases, measured results, failure thresholds, and rerun instructions.
9. **Economics and capacity model** — representative task costs, cached and uncached behavior, output and reasoning costs, latency, concurrency, rate limits, and budget alerts.
10. **Security and protected-data holdpoint register** — public-model boundary, future protected-data prerequisites, residual risks, responsible owners, and specialist gates.
11. **Phase 1 architecture decision set** — accepted choices, deliberately deferred choices, evidence required before later selection, and migration conditions.
12. **Phase 0 exit and build-authorization record** — acceptance result, exact reviewed revision, evidence, unresolved blockers, exceptions, revalidation date, and explicit Phase 1 authorization or denial.

## Acceptance criteria

The gate may close only when all of the following are true:

- The repository-wide audit covers the frozen foundations, accepted decisions, roadmap, governance, architecture, policies, schemas, packages, applications, tools, tests, fixtures, open holdpoints, and current status.
- Material contradictions, stale authority claims, and hidden decisions are corrected or recorded as explicit production-blocking holdpoints.
- Frontier-model-first development is defined as a cognitive and development posture, not a transfer of canonical or governance authority to a model.
- The repository and deterministic systems remain the durable source of truth; no critical state depends only on a model session, hidden scratchpad, provider memory, or chat transcript.
- A compact constitutional kernel and machine-readable authority map are defined and validated.
- Ordinary tasks can operate from bounded context packages with source revision, authority, evidence, and affected-surface provenance.
- Whole-repository review has a separate reproducible path and is not required for every ordinary change.
- Effective-context performance is measured against large, conflicting, stale, superseded, irrelevant, and adversarial inputs; advertised context size is not accepted as evidence by itself.
- Context budgeting reserves capacity for instructions, tools, reasoning, and output rather than filling the nominal window with repository text.
- Retrieval, compaction, caching, refresh, conflict, and stale-context behavior are explicit and testable.
- Models, providers, tools, retrieval systems, memory systems, queues, schedulers, storage systems, and infrastructure remain replaceable adapters rather than domain authority.
- A provider or model can be unavailable or replaced without preventing complete manual personal-core behavior.
- Model and tool outputs cannot create Chronicle truth, permission, execution completion, gameplay completion, rewards, clinical authority, production readiness, or governance authority.
- Every consequential model-assisted path has deterministic validation, human or institutional acceptance where required, source-linked evidence, and containment or rollback behavior.
- Public and synthetic development cannot access production health data, credentials, protected mappings, private provider records, private contracts, security evidence, estate records, or protected financial sources.
- Any future protected-data model path remains blocked behind explicit privacy, security, legal, provider, retention, deletion, incident, and user-control review.
- The modular-monolith default, bounded domains, dependency direction, authoritative write ownership, durable-work semantics, local simulation, and evidence-gated decomposition are reconfirmed against the actual Phase 0 repository.
- The smallest trustworthy Phase 1 implementation slice is defined without prematurely selecting unnecessary production services or irreversible providers.
- Representative model usage has measured cost, latency, caching, failure, and capacity evidence with budget and concentration controls.
- Long-context, retrieval, provider, tool, and agent evaluations can be rerun against future model versions.
- All unresolved architecture questions have an owner, status, evidence requirement, trigger, and holdpoint.
- The final record explicitly states either **AUTHORIZED FOR PHASE 1**, **AUTHORIZED WITH NAMED HOLDPOINTS**, or **BLOCKED**.
- No Phase 1 private-product implementation begins unless the accepted result authorizes it.

## Build-authorization outcomes

### AUTHORIZED FOR PHASE 1

All Phase 0 exit requirements are satisfied at the evidence level required for the bounded Phase 1 slice. Remaining questions are later-phase choices and do not undermine the accepted architecture or player-rights floor.

### AUTHORIZED WITH NAMED HOLDPOINTS

The bounded Phase 1 slice may begin, but specified capabilities remain unavailable until their owners, evidence, specialist review, and acceptance criteria are satisfied. Holdpoints must be narrow, visible, testable, and incapable of being bypassed through model or provider convenience.

### BLOCKED

Phase 1 private-product implementation may not begin. The record must identify the blocking contradiction, missing authority, unbounded risk, unsupported dependency, unavailable evidence, or unresolved architecture decision and define the correction path.

## Explicit non-scope

This Phase 0 gate does not by itself:

- select or purchase a production model, provider, cloud, database, queue, scheduler, workflow engine, vector store, analytics system, observability system, identity provider, EHR, connector, or institutional partner;
- authorize production health-data processing, private model egress, clinical behavior, research, enterprise operation, legacy access, fundraising, financial operation, or deployment;
- claim that one model can reason perfectly over the complete repository;
- require that every request use the largest available context window or most expensive model;
- require a token, blockchain, DAO, legal entity, treasury, or production infrastructure before its own entry gate;
- replace legal, privacy, security, clinical, accessibility, interoperability, operational, financial, or research specialist review; or
- treat founding-steward or model-assisted review as independent certification.

## Revalidation triggers

The architecture audit must be revisited when any of the following materially changes:

- a Phase 1 implementation diverges from the authorized build map;
- a new authoritative domain or consequential agent/tool surface is introduced;
- protected health data is proposed for model, retrieval, memory, or provider processing;
- a model or provider becomes a critical dependency or concentration risk;
- effective-context evaluations materially regress or reveal hidden failure;
- context, caching, retrieval, memory, tool, or agent architecture changes substantially;
- costs, latency, rate limits, or provider terms undermine the accepted operating model;
- a separate service, workflow engine, vector database, or major infrastructure dependency is proposed;
- a security, privacy, authority, or provenance incident invalidates an assumption;
- a better architecture becomes practical because model capability or economics materially improve; or
- the Product Constitution, frozen Architecture Foundation, or accepted model-authority boundary changes through decision record.

## Handoff to Phase 1

The accepted audit must leave Phase 1 with:

- one explicit bounded implementation slice;
- a reviewed context and model architecture;
- stable domain and authority boundaries;
- reproducible evaluation and validation paths;
- named providers only where evidence requires a current selection;
- replacement and degraded-mode behavior;
- protected-data and specialist holdpoints;
- measurable cost and operability expectations; and
- an exact build-authorization record.

The purpose is not to predict the final frontier-model landscape. It is to make Calypso’s Promise capable of improving with that landscape while remaining understandable, correctable, provider-independent, private by design, and faithful to the Promise.
